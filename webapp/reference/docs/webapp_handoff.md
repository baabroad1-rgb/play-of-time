# Play of Time — Handoff for Web App

> Полный срез домена и механик по состоянию на **v12.87 (июль 2026)**. Пишется для
> команды, которая будет делать **web-версию** с нуля. Платформенно-независимо;
> Android-специфика (Compose/Room/Koin) опущена, кроме мест, где механика зависит
> от особенностей ввода (тайминг касания) — там даны веб-эквиваленты.

---

## 1. Что это за игра

Тренажёр «чувства времени» по методике психотехники Геллерштейна. Один цикл:

1. Игрок жмёт **RUN** (Старт).
2. Ждёт ~3 секунды «внутренним счётом».
3. Жмёт **STOP** (Стоп), стараясь попасть ровно в **3.000 с**.
4. Приложение считает ошибку, начисляет **Serenity Coins**, ведёт по квестам.

Цель — научиться стабильно и точно отмерять 3 секунды. Точность растёт по уровням:
десятые → сотые → тысячные доли секунды.

---

## 2. Точность (уровни отображения) и условие победы

Три «кода-уровня» точности (`Accuracy`):

| Level | Accuracy | Отображение | Ячейка (шаг) | Aim |
|---|---|---|---|---|
| L1 | DECISECONDS | `3.0` | 100 мс | 3.000 |
| L2 | CENTISECONDS | `3.00` | 10 мс | 3.000 |
| L3 | MILLISECONDS | `3.000` | 1 мс | 3.000 |
| (SECONDS — не используется в игре) | | `3` | 1000 мс | |

**Победа (true three)** попытки: `|записанное_время_мс − 3000| ≤ tolerance_мс`.
На baseline `tolerance = 0` → нужно попасть в 0 мс ошибки на шкале уровня:
- L1: ошибка ≤ полклетки → округляется в `3.0`
- L2: → `3.00`
- L3: → ровно `3.000`

Толеранс `t` появляется только в индульгированных ROW-субквестах (см. §4).

## 3. Честный подсчёт касания — КРИТИЧНО для веба

**Проблема.** Метка касания квантуется: панель/браузер отдают события ввода
дискретно. На L3 (нужна точность 1 мс) это ломает справедливость — ровно 3.000
может физически «не попадать» на сетку достижимых значений и почти не выбиваться.

На Android базовая частота опроса тача ~120–250 Гц → сетка 4–8 мс. **В вебе то же
самое**: `pointerdown`/`mousedown` timestamps квантованы, `requestAnimationFrame`
~16.7 мс (60 Гц), `event.timeStamp` имеет ограниченное разрешение (в целях защиты
от timing-атак браузеры округляют до ~1 мс и добавляют джиттер). То есть у веба
СВОЯ сетка квантования, и «ровно 3.000» будет так же проваливаться.

**Решение — дизеринг (dithering).** К измеренной длительности прибавляется
равномерный случайный шум шириной в **одну ячейку сетки**, затем округление до мс:

```
record_ms = round( raw_ms + uniform(−cell/2, +cell/2) )
```

Это декоррелирует ошибку квантования → **вероятность каждого значения (включая
ровно 3.000) становится равной**. Стандартная сигнальная техника. Ключевые правила:

- Ширина шума = **половина измеренной ячейки** (адаптивно). Мерить интервалы между
  семплами ввода вживую (в вебе — по `getCoalescedEvents()` у pointer events или по
  времени между кадрами). Если частота честная и ячейка ≤ ~1 мс — дизеринг **= 0**
  (не нужен).
- **Только на L3.** На L1/L2 окно победы (±50 / ±5 мс) шире ячейки → сетка не
  мешает, дизеринг там вносил бы лишний шум на границе окна. НЕ дизерить.
- Мерить длительность нужно по **высокоточным монотонным** таймстампам события
  (в вебе: `event.timeStamp` относительно `performance.now()`; НЕ `Date.now()`),
  снятым как можно раньше в обработчике, чтобы не влезала латентность отрисовки.

**Компенсация повторов (echo/re-roll).** Независимый шум дизеринга рассеивает
физические повторы: «близнецы» (две одинаковые ошибки подряд) теряются, а
физическая тройка ровно-3.000 подряд «выживает» лишь ~1.6%. Лечение — привязка к
СЫРОЙ ячейке:

- `cellIndex = round((raw_ms − 3000) / cell)`.
- Если текущая сырая ячейка = ячейке **предыдущей** попытки → отдаём то же
  записанное значение (**echo**). Один бросок дизеринга на «заход» в ячейку.
  Восстанавливает близнецов и серии троек (×16), без храповика (маргинально всё те
  же 25% на попадание).
- **Узкое исключение:** если echo-значение = 2999 или 3001 (ровно ±1 мс) И это
  промах при текущем допуске (`|v−3000| == 1 && 1 > t`) → перебрасываем (свежий
  дизеринг, ещё шанс на 3.000). Только эти два значения.
- **Индульгенция:** при `t ≥ 1` мс 2999/3001 — победы, переброс сам отключается.
- **Без памяти:** хранится ТОЛЬКО предыдущая попытка. Ушёл в другую ячейку —
  забыто; вернулся позже — новый бросок. Сброс на старте сессии.

> Матемодель, инвариант «в сумме ¼», варианты фаз сетки — подробно в
> `docs/touch_sampling.md`.

## 4. Квестовая система

**15 квестов, 3 уровня по 5.** Порядок прохождения строго линейный.

| # | Механика | Точность | Лимит N | Индульгенция | Поздравление |
|---|---|---|---|---|---|
| L1.1 | ONE_ONLY | 3.0 | нет | нет | — |
| L1.2 | TWO_IN_N | 3.0 | 33 | N ±33 | — |
| L1.3 | THREE_IN_N | 3.0 | 33 | N ±33 | — |
| L1.4 | TWO_IN_ROW | 3.0 | нет | нет | — |
| L1.5 | THREE_IN_ROW | 3.0 | нет | нет | You are at Level 2 Now! |
| L2.1 | ONE_ONLY | 3.00 | нет | нет | — |
| L2.2 | TWO_IN_N | 3.00 | 33 | N ±33 | — |
| L2.3 | THREE_IN_N | 3.00 | 33 | N ±33 | — |
| L2.4 | TWO_IN_ROW | 3.00 | 33 (окно) | t ±1 мс | — |
| L2.5 | THREE_IN_ROW | 3.00 | 33 (окно) | t ±1 мс | You are at Level 3 Now! |
| L3.1 | ONE_ONLY | 3.000 | нет | нет | You feel the millisecond! |
| L3.2 | TWO_IN_N | 3.000 | 33 | N ±33 | Two milliseconds nailed! |
| L3.3 | THREE_IN_N | 3.000 | 33 | N ±33 | Three in a window — fantastic! |
| L3.4 | TWO_IN_ROW | 3.000 | 33 (окно) | t ±1 мс | Two ms in a row — incredible! |
| L3.5 | THREE_IN_ROW | 3.000 | 33 (окно) | t ±1 мс | You are the best! |

**Условия победы (`VictoryCondition`):**
- `SESSION` — X попаданий за сессию (без лимита попыток). Здесь X = 1 (ONE_ONLY).
- `ROW` — X попаданий **подряд** (промах рвёт серию).
- `IN_N` — X попаданий в пределах окна N попыток (не обязательно подряд).

**Индульгенция (адаптация) — с L2.2 и далее.** Правило: **только один вид
адаптации одновременно, никогда оба.**
- IN_N-квесты → адаптируется **N** (шаг ±33). Cap: `N ∈ {33, 66, 99}`. `t = 0`.
- ROW-квесты → адаптируется **t** (шаг ±1 мс). Cap: `t ∈ {0,1,2,3}` мс. `N = 33`
  (окно оценки).

При провале **окна** (N попыток без нужной серии/набора) параметр растёт на шаг
(до cap). Следующая сессия стартует с расширенным N/t. Это «субквест».

**Выход из субквеста (`onQuestWindowSuccess`) — 3 правила:**
- **Rule 1:** победа уже на baseline (N=33, t=0) → advance к следующему квесту.
- **Rule 2:** победа в субквесте с **baseline-quality** результатом → прыжок к
  baseline + advance:
  - ROW: `worstWinError_мс ≤ baseT` (все победные попытки уложились в исходный
    допуск, при baseT=0 — строго 3.000).
  - IN_N: `lastWinIndex ≤ baseN` (все нужные победы — в первых baseN попытках окна).
- **Rule 3:** победа в субквесте, но не baseline-quality → шаг назад на одну
  ступень индульгенции (нужно ещё одно окно). Квест НЕ засчитан для advance, но
  условие сессии выполнено (для индикатора успеха — зелёный палец).

**Полное прохождение** — после L3.5.

## 5. Serenity Coins (SCM) — валюта/метрика

Начисляется **за попытку**, зависит от ошибки текущей и двух соседних попыток
(сглаживание). Формула (из `measures.docx` / `parametr_table.docx`):

```
Tᵢ  = длительность попытки в мс (record)
tᵢ  = |Tᵢ − 3000|              (абсолютная ошибка, мс)

denom = 3·tᵢ + tᵢ₋₁ + tᵢ₊₁
        + |Tᵢ − Tᵢ₊₁| + |Tᵢ − Tᵢ₋₁| − |Tᵢ₊₁ − Tᵢ₋₁|/3
        + 1

levelFactor = 10^(accuracyOrdinal − 3)     // L1=1→×0.01, L2=2→×0.1, L3=3→×1

SCM = 99 / denom · levelFactor
```

- Идеальная попытка (0 мс) → `SCM = 99 · levelFactor`. Пики: L1 → 0.99, L2 → 9.9,
  L3 → 99.
- Level-фактор делает коин «одинаково дорогим по работе точности»: L3 в 100× сложнее
  L1, поэтому L1-коин весит 1/100 L3-коина. Иначе L1 стал бы фермой коинов.
- Считается по `accuracy` **самой попытки** (историю пересчитывать корректно).
- `SCM ≥ 0` всегда (denom ≥ 1). Соседние попытки на краях (первая/последняя) —
  используют доступного соседа (или себя).

Отображение баланса: малые < 10 → 2 знака, < 100 → 1 знак, < 1000 → целое, ≥ 1000 —
пробел-разделитель тысяч.

## 6. Главный экран — элементы

Сверху вниз:

1. **Quest Progress** (визуальный, метафора лучника). Три части:
   - **Мишени** (bullseye) — сколько нужно попаданий (2/3). Поражённая = зелёный
     wash + бейдж с чеком. Компоновка: IN_N/ONE_ONLY — с зазором; ROW — внахлёст
     (цепочка).
   - **Пучок стрел** — «боезапас»: тает по остатку окна (33/66/99 → сколько
     осталось попыток).
   - **Инфо-строка:** `Level N · quest/subquest Y of 5` + `aim: 3.000 [± t] [in row
     × k/m] · left <remaining>/<N>`.
2. **Иконка «?»** — режим интерактивной справки (тап по элементам → бабл-описание).
3. **Cheer-up бабл** — полупрозрачный янтарный оверлей поверх квеста (см. §10).
4. **Кнопка секундомера** (RUN → бег → STOP → результат). Тёмный фон `#2D2D2D`,
   после стопа — сплошной цвет по результату (зелёный/красный/синий, непрозрачно).
   Внутри — крупное время; иконка STOP зеленеет с 2.0 с. После победы — **HOORAY!**
   + аудио, затем **RESET**.
   - **Progress bar** над цифрами: горизонтальная полоса, окно `3.000 ± half`.
     Масштаб **Auto по уровню** (по умолч.): L1 ±600, L2 ±150, L3 ±60 мс; либо ручной
     пресет из Settings (±10…±3000, «2–4 s», «0–4 s»).
   - Смайлик-индикатор тренда (NICE/SAD) в углу кнопки — по сравнению |ошибки| с
     предыдущей.
5. **Error-Pattern chip** (оранжевая плашка) — паттерны и транзиентные сигналы (§9).
6. **Гистограмма распределения ошибок** (Distrib.):
   - 71 бакет, шкала ±dynamicScaleMax (по видимым попыткам). Центр = 0 мс.
   - Цвет столбика: **зелёный — ВСЕГДА только центральный бакет (ровно 3.000)**,
     даже в индульгированных субквестах; иначе красный (early) / синий (late).
   - Горизонтальные линейки приглушены, нумерация Y — только справа.
   - Пунктирные линии геом-средних (early красн., late син., absolute бел.).
   - Оверлей `Σtries` (кол-во) и монетка `Σ SC` (сумма).
7. **GeomMeanRow** — маркеры early/late/absolute на шкале + значения (подписи
   Early/Absolute/Late убраны, цвет кодирует сторону).
8. **Лог попыток / «таблица результатов»** (список, новейшие сверху):
   - Колонки: `# номер (мелкий)` · `время (цвет по типу)` · `бар ошибки со
     значением` · `SC`.
   - Разделители сессий: `─── Session #N · dd/MM/yyyy ───` + палец успеха.
   - **Близнецы** — зелёный «от руки» овал вокруг двух подряд попыток с одинаковой
     |ошибкой|. **Neighbor** — жёлтый овал (|ошибки| различаются ровно на 1 клетку).
   - Пунктиры геом-средних мягкие.
9. **Нижняя навигация** (sticky): Play · Analytics · Settings · About · Export.
   Вкладка **Analytics** = стрелочный **индикатор баланса** (red/blue) на всех
   экранах.

## 7. Экран Analytics — метрики

Период-фильтр (sticky pill): **Session / Day / Month / All time** (общий с главным).

Карточки:
- **CHANCE OF WIN:** Hit rate (доля троек), Attempts per win, **Lucky index**.
- **RANGE OF DEVIATIONS:** attempts ratio (red·green·blue), стрип-градиент red→blue
  с зелёной линией «serenity point» (0), значения P3/P97 (−59 мс / +56 мс), встроены
  **Modes** (2 самые частые ошибки: red + blue, формат `0.006 × 350`).
- **GEOMETRIC MEAN + VARIABILITY:** геом-среднее early/late/absolute + разброс (geom
  CV%).
- **PACE OF LEARNING** (periodScm / periodTotal), **PACE OF PLAY** (att/min,
  min/day).
- **Дерево сессий** Year → Month → Day → Session. Колонки: `lucky` · `mean
  (early/late)` · `att4win`. У **дней** — палец вверх/вниз по большинству успешных
  сессий. У **сессий** — палец успеха (`isQuestComplete`), lucky = число либо
  `no luck` если ни одной тройки.

**Формулы метрик:**

*Geometric mean* (early/late/absolute): `exp(mean(ln(values)))` по ошибкам (early —
только ранние, late — только поздние, absolute — знаковое смещение центра масс
длительностей `geomMean(durations) − 3000`). Разброс = `(exp(std(ln)) − 1)·100 %`.

*Range of deviations:* P3 и P97 перцентили знаковых ошибок (левая/правая границы).

*Modes:* самые частые значения ошибки, округлённые к точности **попытки**
(100/10/1 мс), с `count ≥ 2`; нули отброшены; топ-1 red + топ-1 blue.

*Lucky index* (БОЛЬШЕ = ЛУЧШЕ):
```
slotMs      = 100 / 10 / 1     (по большинству попыток / уровню)
outcomeSlots= range / slotMs + 1
dispersion  = 1 / outcomeSlots           // теор. вероятность попасть в 0 наугад
empirical   = trueThreeWins / attempts
lucky       = empirical / dispersion
```
Lucky > 1 — играешь лучше случайного; это про внимание/антиципацию, не про удачу.

*Balance* — стрелка от red к blue: `ratio = (blue − red)/(red+blue)`, наклон ±80°.
Зелёный кончик при |ratio| < 0.15 (баланс).

## 8. Детекция близнецов / соседей

- **Twin (близнец):** две подряд попытки (обе не-победы) с **одинаковой |ошибкой|**
  (совпадение ≤ 0.5 мс). Знак не важен (обе early, обе late, или ±равные).
  → зелёный овал в логе + транзиент `wow, twins!`.
- **Neighbor (сосед):** |ошибки| двух подряд различаются ровно на **1 клетку**
  уровня (напр. 0.003 и 0.002). → жёлтый овал.
- **It was close:** промах ровно на 1 клетку ЗА пределом допуска (baseline: 2.999 /
  3.001 на L3; в субквесте сдвигается на `t + клетка`). → транзиент `it was close!`.

Вероятности (см. обсуждение): строгий знаковый близнец на L3 при σ≈20 мс ~1.4% на
пару; три одинаковых подряд ~0.02% (1 к ~4300). Растёт квадратично с кучностью.

## 9. Error-Pattern chip (паттерны ритма)

Оранжевая плашка под кнопкой. 7 устойчивых паттернов + транзиенты:

| Паттерн | Текст | Условие |
|---|---|---|
| SYSTEMATIC_EARLY | `← too tense — try to relax` | 9 подряд, все early |
| SYSTEMATIC_LATE | `→ too relaxed — try to focus` | 9 подряд, все late |
| INCREASING_DRIFT | `↗ errors growing — breathe and refocus` | 6+ подряд, |error| строго растёт |
| TRIPLE_IDENTICAL | `✦ three identical — now improve accuracy` | 3 одинаковых + 4-я другая |
| PAUSE_SHORT | `← too tense — lengthen the pause` | 3 паузы < 300 мс И все early |
| PAUSE_LONG | `→ too relaxed — shorten the pause` | 3 паузы > 300 мс И все late |
| JAGGED_RHYTHM | `↯ approaching to the balance` | последние 4 — чередование знака |

Транзиенты (1 сек, приоритетнее): `✦ wow, twins!`, `✦ it was close!`.

## 10. Cheer-ups (пост-эвентные баблы)

Полупрозрачный янтарный бабл (rgba(245,192,46,0.65), тёмно-коричневый текст) с
крестиком и опциональным CTA **«See your progress →»** (ведёт на Analytics; появляется
c L2.2). Триггеры и тексты (plain English, без техножаргона типа «window/attempt»):

| Trigger | Текст |
|---|---|
| AFTER_QUEST | Quest done. Next: hit {phase}. |
| AFTER_LEVEL | Level {N} done: 5/5 quests, {attempts} attempts, {trueThrees} clean threes. Precision now moves to {nextPrecision} of a second. Next: hit {phase}. |
| AFTER_GAME | All 15 quests done: … Well done. Share the Excel … playoftime@gmail.com · chat @champions · news www.playoftime.lol |
| AFTER_SUBQUEST_ENTER | Not enough wins in the last window. The task is eased. Now: hit {phase}. Beat this and the original quest returns. |
| AFTER_SUBQUEST_DEEPER | Still not enough wins. Task eased one more step. Now: hit {phase}. |
| AFTER_SUBQUEST_CAPPED | The task is as easy as it can get. Now: hit {phase}. Slow down, focus, land them. |
| AFTER_SUBQUEST_STALLED | Still not landing at the easiest setting. Take a break … task waits: hit {phase}. |
| AFTER_SUBQUEST_STEPBACK | Good pass. Task tightens one step. Now: hit {phase}. |
| AFTER_SUBQUEST_TO_BASELINE | You hit the original goal even in the eased version. Original quest counted as done. Next: hit {phase}. |
| AFTER_SIMPLIFIED_QUEST_DONE | You climbed back to the original goal and took it. Next: hit {phase}. |

`{phase}` = `describePhase()`: aim + допуск + сколько раз + условие (напр.
`3.00 ± 0.01, twice in 33 attempts`), пробелы — NBSP (не разрываются при wrap).
С L2.2 к success-баблам дописывается сравнение со средним («You beat your average —
24.3 ms this quest vs 31.7 ms overall»).

Звук: `hooray` при появлении зелёной победы; `sorry` при провале квеста.

## 11. Settings (порядок)

1. Cheer-ups (вкл/выкл)
2. Sound
3. Vibration
4. Beats per second (метроном; активен если sound/vibration вкл)
5. Numeric time (числовой отсчёт на кнопке)
6. Progress bar (вкл/выкл)
7. Progress bar scale — чипы: **Auto** (по уровню, по умолч.) / ±10…±500 / 2–4 s /
   0–4 s
8. Playing hand — Left / Right (сохраняется с каждой попыткой для статистики; на

## 13. Модель данных и экспорт

**Session:** `id, startTime, endTime, questLevelId, questTaskId, isQuestComplete,
activeTimeMs` (чистое время экрана, не wall-clock).
**Attempt (Try):** `id, sessionId, startTime, endTime (мс, wall), hand, scm,
toleranceMs (допуск в момент попытки), accuracy`.
- `error = (endTime − startTime) − 3000` мс; `isWin = |error| ≤ toleranceMs`.
- `duration` в БД = `startTime + record` (после дизеринга) — чтобы сходилось с
  «clean threes = endTime − startTime == aim».

**Excel-экспорт** (7 колонок): `Date, Time, Session number, Attempt number, Attempt
result ms, Error time ms, Accuracy`. Играет роль формата обмена/бэкапа.

Play-time: тикер идёт, только когда главный экран активен И сессия открыта
(`activeTimeMs`).

## 15. Порядок реализации для веба (рекомендация)

1. **Таймер и честный замер.** `performance.now()` + `event.timeStamp`, снятые в
   обработчике `pointerdown` (не `click`). Мерить `raw = stop_ts − start_ts`.
2. **Дизеринг + компенсация** (§3) — сразу, иначе L3 будет несправедлив. Измерять
   ячейку по `pointermove.getCoalescedEvents()` / межкадровым интервалам.
3. **Квестовый конечный автомат** (§4): состояние в localStorage/IndexedDB —
   `currentLevelId, currentTaskId, questCurrentN, questCurrentToleranceMs,
   questWindowAttempts/Wins, worstWinErrorMs, lastWinIndex, questWasIndulged`.
4. **Запись попыток/сессий** (§13) + SCM (§5).
5. **Аналитика** (§7) — метрики поверх сохранённых попыток.
6. **UI**: главный экран (§6), Analytics (§7), Settings (§11), About (§12).
7. **Cheer-ups / patterns / twins** (§8–10) — поверх.

**Осторожно на вебе:**
- `Date.now()` немонотонен (NTP) — только `performance.now()` для длительностей.
- Разрешение `event.timeStamp` браузеры режут (~1 мс + джиттер) как раз ради
  анти-timing — это ЕЩЁ ОДНА причина дизерить, а не бороться с этим.
- 60 Гц rAF ≠ частота ввода; pointer events могут коалесцироваться — разбирать
  `getCoalescedEvents()` для честной частоты.
- Вкладка в фоне троттлит таймеры — учесть в play-time и в тикере.
