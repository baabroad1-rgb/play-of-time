## ПРИОРИТЕТ 1 — Баги (исправить в первую очередь)

### 🐛 Баг 1.1 — Ведущий ноль в счётчике

**Файл:** `Utils.kt`, функция `formatTime(Long, Accuracy)`

**Проблема:** При `Accuracy.DECISECONDS` формат `"%03.1f"` даёт `"03.0"` вместо `"3.0"`. При `Accuracy.CENTISECONDS` — `"%04.2f"` даёт `"03.00"`.

**Исправление:**
```kotlin
Accuracy.DECISECONDS  -> String.format(Locale.US, "%.1f", timeSeconds)
Accuracy.CENTISECONDS -> String.format(Locale.US, "%.2f", timeSeconds)
```

Убрать ведущий `0` — форматы `%03.1f` и `%04.2f` нужны только если нужны нули перед целой частью. Здесь не нужны.

**Edge cases:** Проверить вывод для 0.0, 0.9, 1.0, 3.0, 3.999.

---

### 🐛 Баг 1.2 — Время игры сбрасывается после 24 часов

**Файл:** `TotalTimeSpendUseCase.kt` или UI `StatScreen`

**Проблема:** `TotalPlayTime` — сумма длительностей сессий в мс. При отображении через `SimpleDateFormat("HH:mm:ss")` или UTC-форматирование значения > 86 400 000 мс (24 часа) срезаются.

**Исправление:** Вместо форматирования как времени суток — считать как чистые часы:
```kotlin
val totalHours = totalMs / 3_600_000.0
// Отобразить: "%.2f h".format(totalHours) или "Xh Ym"
```

По документу (`plan4revision_v10.docx`): «Можно оставить только количество часов с двумя знаками после запятой» → `"17.43 h"`.

---

### 🐛 Баг 1.3 — Попытка не засчитывается на квесте 2.2 с первого попадания

**Логика:** При `VictoryCondition.IN_N` счётчик `questWindowWins` обновляется в `checkVictory()` только если `currentQuest.maxAttemptsDefault != null`. Квест 2.1 (`ONE_ONLY`, `maxAttemptsDefault = null`) → N-блок пропускается → всё ок. Квест 2.2 (`TWO_IN_N`, `maxAttemptsDefault = 33`) — нужно проверить, засчитывается ли первое попадание в таблицу попыток.

**Предположение из документа:** «если с первого раза выбить 3.00, попытка не засчитывается и в нижнюю табличку не попадает». Скорее всего race condition: `currentSession == null` при первом нажатии, `sessionId` ещё не записан → `addAttempt` пропускается. Уже есть защита `?: getCurrentSessionId()?.id ?: return@launch` — проверить, не срабатывает ли `return@launch` на первой попытке.

**Как проверить:** Запустить квест 2.2 → первая попытка → выбить 3.00 → убедиться что попытка есть в таблице.

### 📊 Фича 3.1 — Метрики Надёжность и Саморегуляция

**Откуда:** `plan_of_actions.docx`, `measures.docx` / `parametr_table.docx`

**Определения из документа:**
- **Надёжность** — насколько стабильно игрок достигает результатов определённой точности. Формула: `DeviationProfile` (медиана + σ%) — уже считается в `AnalyticsUseCase`.
- **Саморегуляция успокоения** — как быстро после 9 красных подряд игрок возвращается к норме (уменьшение |ошибки|). Измеряется количеством попыток до возврата к предшествующей медиане.

**Что уже есть:** `DetectCheerUpTriggerUseCase` детектирует `NINE_RED` / `NINE_BLUE`. `AnalyticsUseCase` считает `deviationAll`, `deviationEarly`, `deviationLate`.

**Что добавить:**
1. В `AnalyticsData` — новые поля: `reliabilityPct: Double` (= `100 - stdPct` из `deviationAll`), `selfRegCalmingAttempts: Int?`, `selfRegActivationAttempts: Int?`
2. В `AnalyticsUseCase` — постобработка: после детекта NINE_RED/NINE_BLUE найти момент возврата к медиане ± допуск
3. В `StatScreen` — отобразить в секции Summary

**Не входит в scope v1:** Исторический график саморегуляции по сессиям.
