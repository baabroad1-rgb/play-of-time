# Сборки: раздача пользователям и архив версий

Это две разные задачи, и решаются они по-разному. Путать их не надо.

## 1. Раздача пользователям — остаётся на хостинге, ничего не меняется

APK лежит на `playoftime.online` в папке `downloads/`, отдаёт его
`webapp/api/latest_apk.php`. Инструкция по выкладке — `webapp/downloads/README_update_deploy.md`.
Этот механизм **не трогаем**: он единый источник правды сразу для двух вещей —
кнопки «download app apk» на сайте и самообновления внутри приложения
(`android/app/src/main/java/ru/iflex/timemvp/core/update/UpdateApi.kt` делает
HEAD-запрос на тот же URL и достаёт версию из `Content-Disposition`).

**Почему не через GitHub Releases.** Репозиторий приватный, а ассеты релизов
приватного репозитория скачиваются только с токеном авторизации: по прямой ссылке
без логина GitHub отдаёт 404. То есть ни браузер посетителя сайта, ни приложение
APK оттуда не получат. Перевод раздачи на Releases сломал бы и кнопку на сайте,
и самообновление.

Если раздача с GitHub когда-нибудь понадобится, вариантов два: отдельный
**публичный** репозиторий только под релизы, либо выход в Google Play — после
которого вся native-часть самообновления удаляется целиком (см. раздел
`⚠️ УДАЛИТЬ ПРИ ВЫХОДЕ В GOOGLE PLAY` в `android/CLAUDE.md`).

## 2. Архив версий — вот это стоит завести

APK в git не хранятся (`*.apk` в `.gitignore`, и правильно: 26 МБ на каждую
версию раздули бы репозиторий). Следствие: **вернуться к старой сборке сейчас
нельзя.** Если игрок сообщит о баге на v13.90, воспроизвести именно ту сборку
не на чем — APK с хостинга к тому времени уже перезатёрт следующим.

Releases приватного репозитория для этого подходят полностью: команда авторизована,
а посторонним архив сборок и не нужен.

### Как выложить сборку в архив

Тег — ровно `versionName` из `android/app/version.properties` с префиксом `v`:
`versionBase=14` + `versionPatch=13` → тег **`v14.13`**.

**Через веб-интерфейс:** [Releases](https://github.com/baabroad1-rgb/play-of-time/releases)
→ «Draft a new release» → «Choose a tag» → вписать `v14.13` → «Create new tag on publish»
→ перетащить APK в «Attach binaries» → Publish.

**Через `gh` CLI** (если установлен):

```bash
gh release create v14.13 \
  android/app/build/outputs/apk/debug/play-of-time-v14.13.apk \
  --title "v14.13" \
  --notes "Сборка от $(date +%Y-%m-%d). Изменения — в docs/CHANGELOG.md."
```

### Что писать в описании релиза

Ничего пересказывать не надо — журнал уже есть. Достаточно даты и ссылки на
запись в `docs/CHANGELOG.md`. Смысл релиза здесь — приложенный файл, а не текст.

### Какие версии стоит залить задним числом

Если старые APK ещё сохранились где-то на диске или в архивах — их можно
выложить тегами задним числом, GitHub это позволяет. На момент переезда
в репозитории упоминались `v12.39`, `v13.12`, `v14.02`; сами файлы в git не
попали (исключены по `*.apk`), но если найдутся локально — архив стоит начать
с них.

## 3. Чего тут сознательно нет

**Автосборки в CI.** Собирать APK на GitHub Actions технически можно, но
release-сборку надо подписывать, а для этого `keystore.jks` пришлось бы положить
в секреты GitHub. Ключ подписи — то, потеря или утечка чего лишает возможности
обновлять приложение в Google Play под тем же именем. Пока сборка делается
на одной машине, риск этого не стоит. Если понадобится — обсуждать отдельно,
и начинать с debug-сборок, которые подписывать не нужно.
