# Честный подсчёт касания и частота опроса тачскрина

> Итог расследования 25–26 июля 2026 (v12.68 → v12.84). Держит в одном месте: в чём
> была проблема, какие рычаги включают честную высокую частоту опроса тача, как
> их переключать в коде, и как ПРОВЕРИТЬ результат по данным.
>
> **Актуальное состояние (v12.84):** дизеринг АДАПТИВНЫЙ (ширина = половина
> ИЗМЕРЕННОЙ ячейки, авто-отключение на честной высокой частоте), применяется
> ТОЛЬКО на L3 (миллисекунды), и снабжён КОМПЕНСАЦИЕЙ echo/re-roll по сырой ячейке
> (чтобы дизеринг не рассеивал физические повторы — близнецов и серии троек). См.
> разделы «Адаптивный дизеринг» и «Компенсация» ниже — они отражают текущий код;
> более ранние разделы про фикс-константу `DITHER_HALF_MS` оставлены как история.

## Проблема

На L3 (миллисекунды) «ровно 3.000» почти не выбивалось. Анализ 4013 реальных
попыток (Excel-экспорт) показал: записанные длительности **неравномерны** —
значения ложатся полосами через ~8 мс, а ровно 3.000 попадает в провал.

- `duration mod 10` — равномерно (χ²≈12, нет квантования на 1-мс уровне).
- `duration mod 8` — резко неравномерно (**χ²≈4890**, пик/впадина 34×). Это
  8-мс сетка.
- Ровно 0 (тройка): 2 попадания из 3491; соседи ±2/±3 — по ~150. Ноль подавлен
  ~32×.
- Винрейт: L2 (±5 мс окно) 12.9% vs L3 (точный 0) 0.06%.

### Причина (важно не путать)

**8 мс — это НЕ предел тач-панели.** Тач-панель современных телефонов семплит
480–1000 Гц (игровые режимы). 8-мс сетка — это **дефолтная частота, на которой
Android доставляет касания приложению**: события батчатся под кадр дисплея, а
панель по умолчанию держит низкую частоту опроса (~120 Гц). `120 Гц` — это
refresh ЭКРАНА, к тачу отношения не имеет.

Регрессию проявил фикс латентности 14 июля: раньше длительность мерилась
`System.currentTimeMillis()` ПОСЛЕ диспетчера — случайный джиттер 10–20 мс
работал как дизеринг и размазывал сетку («раньше работало справедливо»). Переход
на точный kernel-таймстамп (`PointerInputChange.uptimeMillis`) убрал джиттер и
оголил сырую 8-мс сетку.

## Решение: включить честную высокую частоту опроса тача

Два рычага в коде + один способ проверки. Цель — заставить ОС отдавать касания на
максимальной частоте панели, чтобы метка касания была честной (без 8-мс сетки),
БЕЗ искусственного шума.

### Рычаг 1 — Android Game Mode (главный)

Приложение, помеченное как игра, получает **GAME power mode**, и на
поддерживающих устройствах ОС поднимает частоту опроса тач-панели до максимума
(тот самый «разгон до 480–700 Гц в играх»).

**Где:** [`app/src/main/AndroidManifest.xml`](../android/app/src/main/AndroidManifest.xml),
тег `<application>`:

```xml
<application
    android:appCategory="game"
    android:isGame="true"
    ... >
```

**Как переключать:** убрать/добавить эти два атрибута. `appCategory="game"` —
основной сигнал (AOSP: «GAME power mode всегда установлен для приложений с
appCategory=GAME»). `isGame="true"` — легаси-дубль для старых устройств.

**Каталог:** это также категоризирует приложение как игру в Google Play. Если это
нежелательно для стора — оставить только для debug-сборки или обсудить.

Док: <https://source.android.com/docs/core/perf/boost>,
<https://developer.android.com/games/optimize/adpf/gamemode/gamemode-api>.

### Рычаг 2 — requestUnbufferedDispatch (вторичный)

Просит систему НЕ батчить тач-события, а отдавать сразу. Действует **до
ACTION_UP** (per-gesture), поэтому пере-арм на каждом жесте.

**Где:** [`StopWatchButton.kt`](../android/app/src/main/java/online/playoftime/ui_lib/stop_watch/StopWatchButton.kt).
Функция `requestHiRateTouch()` + её вызовы:

```kotlin
val view = LocalView.current
fun requestHiRateTouch() {
    if (android.os.Build.VERSION.SDK_INT >= 33) {      // (int source) — API 33+
        runCatching {
            view.requestUnbufferedDispatch(android.view.InputDevice.SOURCE_TOUCHSCREEN)
        }
    }
}
LaunchedEffect(Unit) { requestHiRateTouch() }          // при входе на экран
// ...и в pointerInput на КАЖДЫЙ down:
awaitEachGesture {
    val down = awaitFirstDown(pass = PointerEventPass.Initial)
    requestHiRateTouch()                               // пере-арм на жест
    ...
}
```

**Ограничение:** сам по себе `requestUnbufferedDispatch` действует на события
ПОСЛЕ down (move/up) и метку самого DOWN не улучшает — реальный подъём частоты
даёт Game Mode (рычаг 1). Держим оба.

Overload `requestUnbufferedDispatch(int source)` — API 33; overload
`(MotionEvent)` — API 21, но требует raw MotionEvent (в Compose pointerInput его
нет, есть `PointerInputChange`). compileSdk=34 → guard по `SDK_INT >= 33`.

### Метка времени касания (уже честная)

Берём kernel-таймстамп касания: `awaitFirstDown(pass = PointerEventPass.Initial)`
→ `down.uptimeMillis`. Это момент, когда СЕНСОР зарегистрировал касание (до
Compose-диспетчера). Разрешение метки — миллисекунды: этого достаточно, чтобы
УВИДЕТЬ сетку тоньше 8 мс (напр. 2 мс при 480 Гц). Sub-ms (getEventTimeNanos,
API 34) не нужен, пока панель не отдаёт быстрее, чем 1 кГц.

## ИТОГ на OnePlus 10 Pro (25 июля 2026): дизеринг ±2 мс

Замер на устройстве (встроенный метр в Settings + анализ 363 попыток):
- Game Mode + unbuffered подняли частоту опроса **со 120 до 240 Гц** (сетка 8→4 мс,
  неравномерность с 34× до ~2×; mod‑2 стал идеально ровным).
- **Но выше не идёт для ТАПОВ.** Драг бурстит до 470 Гц, однако одиночный тап
  ловится на БАЗОВОЙ частоте (~240 Гц), а разогнать её одним касанием за ~1 с
  физически нечем. HyperTouch (до 1000 Гц) OnePlus отдаёт только играм из своего
  курируемого списка — стандартным API не включить.
- Поэтому включён **дизеринг ±2 мс** (`DITHER_HALF_MS = 2.0`) = половина 4‑мс
  ячейки. Остаточная 4‑мс рябь полностью выравнивается, ровно 3.000
  равновероятна. Проверка симуляцией на данных: mod‑4 χ² с 28 → ~0.

Точность = половина ячейки (= половина от 1000/частота): 120 Гц→±4, 240→±2,
480→±1, 1000→±0.5 мс. Встроенный метр (Settings → «Touch sampling rate»)
показывает измеренную частоту и следующую из неё точность вживую.

## Механизм дизеринга (fallback, когда честной высокой частоты для тапа нет)

Контролируемый дизеринг: к длительности прибавляется равномерный шум шириной в
один период сетки, что декоррелирует квантование и делает вероятность КАЖДОГО
значения (включая ровно 3.000) равной. Это ровно то, что раньше случайно делал
джиттер диспетчера.

**Где:** константа в [`Utils.kt`](../android/app/src/main/java/online/playoftime/core/utils/Utils.kt):

```kotlin
const val DITHER_HALF_MS = 2.0   // = половина ячейки сетки. Текущая база 240 Гц
                                 // → 4-мс ячейка → ±2.0. 120→4.0, 480→1.0,
                                 // 1000→0.5. 0.0 = ВЫКЛ (если честная высокая
                                 // частота для тапа реально доступна).
```

Применяется в [`MainViewModel.kt`](../android/app/src/main/java/online/playoftime/features/main/ui/MainViewModel.kt),
STOP-хендлер, при расчёте `attemptDuration`:

```kotlin
val attemptDuration: Long = if (autoStopFired || DITHER_HALF_MS <= 0.0) rawDuration
    else kotlin.math.round(
        rawDuration + kotlin.random.Random.nextDouble(-DITHER_HALF_MS, DITHER_HALF_MS)
    ).toLong()
```

**Как переключать:** `DITHER_HALF_MS = 4.0` — включить, `= 0.0` — выключить.
Guard `|| DITHER_HALF_MS <= 0.0` обязателен: `Random.nextDouble(0.0, 0.0)`
кидает исключение.

**Важно:** дизеринг и высокая частота — ВЗАИМОИСКЛЮЧАЮЩИЕ. Если частота честная,
дизеринг только добавит лишний шум. Держать что-то одно.

## Как проверить (решают ДАННЫЕ, не слова)

Единственный честный способ узнать, включилась ли высокая частота на устройстве —
собрать реальные попытки и посмотреть на равномерность.

1. Поиграть на L3 (≥200–300 попыток) на целевом устройстве.
2. Export → Excel (кнопка Export в нижней навигации).
3. Прогнать тест равномерности (Python, openpyxl):

```python
import openpyxl
from collections import Counter
wb = openpyxl.load_workbook('play_of_time_XXXX.xlsx', read_only=True, data_only=True)
ws = wb.active; rows = list(ws.iter_rows(values_only=True)); hdr = rows[0]
iRes = hdr.index('Attempt result, ms')
d = [int(round(r[iRes])) for r in rows[1:] if r[iRes] is not None]
def chi(vals, m):
    c = Counter(v % m for v in vals); n = len(vals); exp = n / m
    return sum((c.get(k, 0) - exp) ** 2 / exp for k in range(m)), [c.get(k, 0) for k in range(m)]
print('mod 8:', chi(d, 8))   # χ²<14 → РАВНОМЕРНО (сетка ушла); χ²»100 → сетка осталась
print('mod 4:', chi(d, 4))   # проверка на 4-мс сетку (240 Гц)
print('mod 2:', chi(d, 2))   # проверка на 2-мс сетку (480 Гц)
```

Интерпретация `mod 8` (df=7, порог χ²=14.07 при α=0.05):
- **χ² < 14** → распределение равномерное, высокая частота сработала, дизеринг НЕ
  нужен (`DITHER_HALF_MS = 0.0`).
- **χ² в сотнях/тысячах** → 8-мс сетка осталась, Game Mode не поднял частоту на
  этом устройстве → включить fallback (`DITHER_HALF_MS = 4.0`).
- Если сетка уменьшилась до 4 или 2 мс (mod-4/mod-2 неравномерны, mod-8
  равномерен) → частота выросла частично; при желании дизерить на новый, меньший
  период (`DITHER_HALF_MS` = половина нового периода).

## Адаптивный дизеринг (v12.82, актуально)

Фикс-константа `DITHER_HALF_MS` заменена на адаптив: ширина шума = половина
ФАКТИЧЕСКИ измеренной ячейки, замер вживую.

- [`TouchRateEstimator`](../android/app/src/main/java/online/playoftime/core/utils/TouchRateEstimator.kt)
  — singleton, копит межсемпловые интервалы по реальным ТАПАМ (не драгу), медиана →
  ячейка. `ditherHalfMs(fallback)` = половина ячейки, либо **0 если ячейка ≤ 1.2 мс**
  (≈1000 Гц — панель сама разрешает до 1 мс, дизеринг не нужен).
- Кормится в [`StopWatchButton.kt`](../android/app/src/main/java/online/playoftime/ui_lib/stop_watch/StopWatchButton.kt)
  из семплов жеста (`down.historical` + move-семплы) после захвата длительности.
- Последняя ячейка хранится в `LocalStorageService.getTouchCellMs()` (default 4.0 =
  250 Гц) как фоллбэк на старте сессии.
- `Utils.kt`: `DITHER_HALF_MS` удалён → `DEFAULT_TOUCH_CELL_MS = 4.0`.

**Только L3.** Дизеринг применяется исключительно на MILLISECONDS. На L1 (деци,
окно ±50 мс) и L2 (центи, ±5 мс) окно победы ШИРЕ ячейки (~4 мс) → 3.0/3.00 всегда
достижимы, сетка не мешает, дизеринг там только вносил бы шум на границе окна.
`MainViewModel` STOP: `if (accuracy == MILLISECONDS) ditherHalfMs(...) else 0.0`.

## Компенсация: echo/re-roll по сырой ячейке (v12.84, актуально)

Дизеринг независимым шумом РАССЕИВАЕТ физические повторы: два одинаковых сырых
попадания дают разные записи → близнецы теряются; физическая тройка подряд
«выживает» лишь ~1.6% (¼³). Лечение — привязать повтор к сырой ячейке:

- `cellIndex = round((rawDuration − 3000) / cell)` (ячейка 0 центрирована на 3.000).
- **Та же ячейка, что у ПРЕДЫДУЩЕЙ попытки** → отдаём то же значение (echo). Один
  бросок на заход в ячейку → близнецы гарантированы, серия троек ×16 (25% на заход
  вместо 1.6%), без храповика (маргинально те же 25%, инфляции одиночной тройки нет).
- **Узкое исключение:** если echo-значение = 2999 или 3001 (ровно ±1 мс от 3.000) И
  это ПРОМАХ при текущем допуске (`|v−3000| == 1 && 1 > tol`) → вместо копии
  перебрасываем (свежий дизеринг, ещё шанс дожать 3.000). Только эти два значения,
  только на повторе в ту же ячейку.
- **Индульгенция (L3.4/L3.5, t±1..3 мс):** под субквестом 2999/3001 становятся
  ПОБЕДАМИ. Условие `1 > tol` при t≥1 = false → переброс сам отключается, победу не
  выбрасываем (echo как у любой победы).
- **Без памяти:** хранится ТОЛЬКО непосредственно предыдущая попытка
  (`lastDitherCellIndex` + `lastDitherValueMs` в `MainViewModel`). Ушёл в другую
  ячейку — прежнее забыто; вернулся позже в ту же ячейку = новый заход, свежий
  бросок. Никакого кэша «ячейка→значение». Сброс на старте каждой сессии.

**Отвергнуто:** переброс всей полосы 2.997–3.003 — это храповик (resample-until-
success), инфляция троек до ~100% на удержании ячейки. Узкое ±1 мс — компромисс
(~8% относит. инфляции, только на редких повторах в одну ячейку).

Twin-детектор НЕ менялся: echo даёт идентичные значения → близнец срабатывает сам.

## Что НЕ работает / тупики

- **Тонкий допуск победы (±N мс)** вместо честного счёта — отвергнут: 3.002/3.004
  визуально засчитываются «без индульгенций», выглядит как читерство. Победа
  должна быть точной, а честность — на уровне ИЗМЕРЕНИЯ, не окна.
- **getEventTimeNanos без подъёма частоты** — не помогает: точность метки не
  спасает, если сама панель семплит редко.
- **Эмулятор** частоту тач-панели реального телефона не воспроизводит — проверять
  только на устройстве.
