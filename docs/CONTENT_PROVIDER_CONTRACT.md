# Контракт ContentProvider: чтение данных игрока Play of Time

Документ для команды, которая читает данные. Описывает, что отдаёт Play of Time
стороннему приложению на том же телефоне.

**Статус: черновик, до реализации.** Пока провайдера в приложении нет, этот
документ — предмет согласования. После согласования он становится обязательством:
перечисленные имена и смысл колонок менять нельзя, можно только добавлять новые.

Версия контракта: **v1**

---

## Подключение

**Authority:** `online.playoftime.provider`

**Разрешение**, которое читающее приложение объявляет у себя в манифесте:

```xml
<uses-permission android:name="online.playoftime.permission.READ_PLAY_DATA" />
```

Уровень разрешения — `dangerous`: при первом обращении Android спросит игрока.
Разрешение нужно не потому, что данные секретные — имён, контактов и вообще
чего-либо о личности игрока приложение не хранит, — а потому что экспортированный
провайдер без разрешения читает любое приложение на телефоне, и Google Play
помечает это при публикации.

Доступ только на чтение. `insert`, `update`, `delete` возвращают ошибку.

## Адреса

| URI | Что отдаёт |
|---|---|
| `content://online.playoftime.provider/v1/attempts` | каждая попытка отдельной строкой |
| `content://online.playoftime.provider/v1/sessions` | сессии (заход в приложение) |
| `content://online.playoftime.provider/v1/daily` | сводка по дням |
| `content://online.playoftime.provider/v1/meta` | версия контракта и версия приложения |

Версия в пути. Когда состав колонок придётся менять несовместимо, появится `/v2/`,
а `/v1/` продолжит работать.

## О чём вообще данные

Игрок запускает секундомер и пытается остановить его ровно на **3.000 секунды**.
Одно такое нажатие — попытка. Подряд идущие попытки за один заход — сессия.

Всё, что интересно про моторику, выражается через **ошибку**: на сколько
миллисекунд игрок промахнулся мимо трёх секунд. Знак важен: минус — остановил
рано, плюс — поздно.

## `/v1/attempts` — попытки

| Колонка | Тип | Что значит |
|---|---|---|
| `_id` | Long | Идентификатор попытки. Сквозной, не переиспользуется |
| `session_id` | Long | К какой сессии относится |
| `started_at` | Long | Момент нажатия RUN, epoch ms, UTC |
| `ended_at` | Long | Момент нажатия STOP, epoch ms, UTC |
| `duration_ms` | Long | `ended_at − started_at`. Сколько секундомер реально шёл |
| `error_ms` | Long | `duration_ms − 3000`. **Минус — рано, плюс — поздно** |
| `tolerance_ms` | Int | Допуск, который действовал в момент этой попытки (см. ниже) |
| `decimals` | Int | Точность уровня: 2 — сотые, 3 — тысячные |
| `is_hit` | Int | 1 — попадание, 0 — промах. Правило ниже |
| `serenity_coins` | Double, может быть null | Начисленные монеты. `null` означает «ещё не посчитано» |
| `hand` | String | `LEFT` или `RIGHT` — какой рукой играли |

**Про `is_hit`.** Правило не сводится к «ошибка меньше допуска», и повторять его
у себя не нужно — колонка уже посчитана приложением по тому же коду, что рисует
зелёный цвет на экране. Для понимания: ошибка сначала округляется до точности
уровня (`decimals`), затем сравнивается с допуском, а на уровне тысячных ещё и
с физическим полом разрешения экрана — точно ноль пальцем недостижим.

**Про `tolerance_ms`.** В игре есть «индульгенция»: если игрок долго не может
пройти задачу, окно победы временно расширяется. Поэтому у попыток одного уровня
допуск может отличаться, и он сохранён у каждой попытки отдельно. Судить о
качестве моторики честнее по `error_ms`, а не по `is_hit`: последний зависит от
того, была ли в тот момент включена поблажка.

**Про `serenity_coins`.** Монеты за попытку считаются ретроспективно, когда
появляется следующая попытка. Поэтому у самой свежей попытки значение почти
всегда `null`, и через несколько секунд становится числом. Это не ошибка.

Порядок строк по умолчанию: `started_at` по возрастанию.

## `/v1/sessions` — сессии

| Колонка | Тип | Что значит |
|---|---|---|
| `_id` | Long | Идентификатор сессии |
| `started_at` | Long | Первый RUN в сессии, epoch ms |
| `ended_at` | Long | Последний STOP, epoch ms |
| `active_ms` | Long | Сколько игрок **реально** провёл на игровом экране |
| `attempts_count` | Int | Сколько попыток в сессии |
| `hits_count` | Int | Сколько из них попаданий |
| `quest_level` | Int | Уровень квеста на начало сессии, 0 — неизвестно |
| `quest_task` | Int | Задача квеста на начало сессии, 0 — неизвестно |
| `quest_completed` | Int | 1 — в этой сессии квест был завершён |

**Про `active_ms`.** Это не `ended_at − started_at`. Второе — время по настенным
часам, включая моменты, когда игрок ушёл в другое приложение. `active_ms` тикает
только пока игровой экран на переднем плане. Для оценки нагрузки нужен именно он.

Оговорка: у сессий, записанных до сентября 2026, `active_ms` восстановлен как
`ended_at − started_at`, то есть завышен. Отличить их можно по дате.

## `/v1/daily` — сводка по дням

Одна строка на календарный день, в котором была хотя бы одна попытка.
Дни без активности не возвращаются.

| Колонка | Тип | Что значит |
|---|---|---|
| `_id` | Long | Начало дня, epoch ms, местный часовой пояс |
| `date` | String | `YYYY-MM-DD`, местный часовой пояс |
| `attempts_count` | Int | Попыток за день |
| `hits_count` | Int | Попаданий |
| `sessions_count` | Int | Заходов |
| `active_ms` | Long | Суммарное время на игровом экране |
| `mean_error_ms` | Double | Средняя ошибка со знаком. Показывает системное смещение: устойчивый минус — игрок стабильно спешит |
| `mean_abs_error_ms` | Double | Средняя ошибка по модулю. Показывает точность независимо от смещения |
| `early_count` | Int | Сколько раз остановил раньше трёх секунд |
| `late_count` | Int | Сколько раз позже |
| `serenity_coins` | Double | Сумма монет за день |

`mean_error_ms` и `mean_abs_error_ms` — разные вещи, и для моторики полезны обе.
Первая говорит, куда игрока систематически сносит; вторая — насколько он вообще
кучно кладёт попытки. Игрок может стабильно спешить на 40 мс и при этом быть
очень точным.

## `/v1/meta` — одна строка

| Колонка | Тип | Что значит |
|---|---|---|
| `contract_version` | Int | Версия этого контракта, сейчас `1` |
| `app_version_name` | String | Версия приложения, например `14.15` |
| `aim_ms` | Int | Цель в миллисекундах. Сейчас всегда `3000` |
| `attempts_total` | Long | Всего попыток в базе |
| `first_attempt_at` | Long | Самая ранняя попытка, epoch ms |

Читать `meta` перед первым запросом — дешёвый способ понять, есть ли вообще
данные и совпадают ли ожидания по версии.

## Чего в контракте сознательно нет

**Поле `deflection`** из базы. Оно не используется в приложении с весны и всегда
пустое; оставлено в таблице только чтобы не ломать миграции Room.

**Прямой доступ к таблицам.** Отдаётся проекция, а не колонки базы как есть.
Причина не в секретности, а в том, что иначе схема базы замерзает: любая
перестановка внутри приложения ломала бы читающее приложение. Проекцию можно
сохранить неизменной, переписав всё под ней.

Заодно это убирает две ловушки именования. В базе поле `accuracy` — это не
точность, а число знаков после запятой; здесь оно называется `decimals`.
А сама ошибка попытки в базе не хранится вообще, она вычисляется — здесь она
есть готовым числом.

**Запись.** Провайдер только на чтение.

## Что ещё нужно согласовать

1. **Как читающее приложение узнаёт о новых данных.** Варианты: опрашивать
   периодически, либо Play of Time шлёт `notifyChange` и читающая сторона
   подписывается через `ContentObserver`. Второе экономнее, но требует, чтобы
   читающее приложение было к этому готово.
2. **Нужен ли отбор по датам** (`?from=…&to=…`) или достаточно читать всё
   и фильтровать у себя. При нескольких десятках тысяч попыток второе уже
   заметно.
3. **Что делать, если игрок стёр данные в Play of Time.** Есть кнопка полного
   сброса. Идентификаторы после неё начинаются заново, и читающее приложение
   увидит «новую историю» с теми же `_id`. Нужен признак, по которому это видно —
   например, `reset_generation` в `meta`.
