# Чтение данных Play of Time сторонним приложением

Инструкция для приложения, которое читает историю тренировок игрока
с того же телефона.

Версия контракта: **1**
Сверено с кодом: 27.09.2026 (приложение 15.06)

## Подключение

Добавьте в свой `AndroidManifest.xml`:

```xml
<uses-permission android:name="online.playoftime.permission.READ_PLAY_DATA" />

<!-- Android 11+ прячет чужие приложения. Без этого блока провайдер просто
     не найдётся, причём молча — resolver вернёт null. -->
<queries>
    <provider android:authorities="online.playoftime.provider" />
</queries>
```

Разрешение уровня `dangerous` — при первом обращении Android покажет игроку
запрос. Запросите его как обычное runtime-разрешение.

## Адреса

| URI | Что отдаёт |
|---|---|
| `content://online.playoftime.provider/v1/attempts` | все попытки |
| `content://online.playoftime.provider/v1/sessions` | все сессии |
| `content://online.playoftime.provider/v1/meta` | одна строка: версии и объём данных |

Только чтение. `insert`, `update`, `delete` бросают исключение.

Отдаётся вся история целиком, порядок — по `id` по возрастанию. Отбора по
датам сейчас нет; если объём станет проблемой, добавим.

Пример:

```kotlin
val uri = Uri.parse("content://online.playoftime.provider/v1/attempts")
contentResolver.query(uri, null, null, null, null)?.use { c ->
    val startTime = c.getColumnIndexOrThrow("startTime")
    val endTime   = c.getColumnIndexOrThrow("endTime")
    while (c.moveToNext()) {
        val durationMs = c.getLong(endTime) - c.getLong(startTime)
        val errorMs    = durationMs - 3000   // минус — рано, плюс — поздно
    }
}
```

## О чём данные

Игрок запускает секундомер и пытается остановить ровно на **3.000 секунды**.
Одно нажатие — попытка. Подряд идущие попытки за один заход — сессия.

Про моторику говорит **ошибка**: `(endTime − startTime) − 3000`, в
миллисекундах, со знаком. Минус — остановил рано, плюс — поздно.

## `/v1/attempts`

| Колонка | Тип | Что значит |
|---|---|---|
| `id`, `_id` | Long | Идентификатор попытки. Одно и то же значение, `_id` продублирован для курсорных адаптеров Android |
| `sessionId` | Long | К какой сессии относится |
| `startTime` | Long | Нажатие RUN, epoch ms, UTC |
| `endTime` | Long | Нажатие STOP, epoch ms, UTC |
| `accuracy` | Int | **Это не точность.** Число знаков после запятой: 2 — уровень сотых, 3 — тысячных. Имя историческое, менять его сейчас — ломать нашу базу |
| `toleranceMs` | Int | Допуск, действовавший в момент этой попытки |
| `scm` | Double, бывает NULL | Начисленные Serenity Coins |
| `hand` | String | `LEFT` или `RIGHT` |
| `deflection` | Long, всегда NULL | Мёртвое поле. Не используется с весны, оставлено в таблице чтобы не ломать миграции. **Игнорируйте** |

### Три вещи, которые сэкономят вам отладку

**`scm` у самой свежей попытки почти всегда NULL.** Монеты считаются
ретроспективно — когда появляется следующая попытка. Через несколько секунд
значение появится. Это не битые данные.

**`toleranceMs` у попыток одного уровня разный.** В игре есть «индульгенция»:
если игрок долго не может пройти задачу, окно победы временно расширяется.
Поэтому судить о моторике надо по ошибке, а не по факту попадания —
иначе вы измерите поблажки, а не игрока.

**Попадание считается сложнее, чем «ошибка меньше допуска».** Ошибка сначала
округляется до точности уровня (`accuracy` знаков) и только потом сравнивается
с `toleranceMs`. Если нужен именно наш признак победы, а не своя
интерпретация — скажите, добавим готовую колонку.

**На уровне тысячных в записанное время намеренно добавлен шум.** Это
единственное место, где наши данные не являются чистым измерением, и знать об
этом обязательно.

Тачскрин опрашивает палец не непрерывно, а раз в 4–8 мс. Из-за этого
длительности ложатся полосами по сетке опроса, и некоторые значения — в том
числе ровно 3.000 — выпасть просто не могут. Чтобы распределение было
равномерным, на уровне тысячных к длительности прибавляется равномерный шум
шириной в одну измеренную ячейку сетки (обычно ±2–4 мс). Шум пишется в базу:
`endTime` уже содержит его.

Что из этого следует для анализа:

* на уровне тысячных (`accuracy` = 3) единичная ошибка имеет погрешность
  порядка ячейки опроса — не стройте выводов на разнице в 1–2 мс между
  соседними попытками;
* на средних и распределениях по многим попыткам шум не мешает: он
  симметричный и с нулевым средним, ради этого и сделан;
* на уровнях десятых и сотых (`accuracy` = 1 и 2) шума НЕТ, там время сырое;
* если приложение само измеряет частоту опроса высокой (порядка 1000 Гц),
  шум отключается автоматически и время тоже сырое.

Если в старых обсуждениях вам попадался «физический пол разрешения», расширявший
окно победы на тысячных, — этого механизма больше нет, его заменил дизеринг.

## `/v1/sessions`

| Колонка | Тип | Что значит |
|---|---|---|
| `id`, `_id` | Long | Идентификатор сессии |
| `startTime` | Long | Первый RUN, epoch ms |
| `endTime` | Long | Последний STOP, epoch ms |
| `activeTimeMs` | Long | Сколько игрок **реально** провёл на игровом экране |
| `isQuestComplete` | Int | 1 — в этой сессии квест был завершён |
| `questLevelId` | Int | Уровень квеста на начало сессии, 0 — неизвестно |
| `questTaskId` | Int | Задача квеста на начало сессии, 0 — неизвестно |

**`activeTimeMs` — не `endTime − startTime`.** Второе считает по настенным
часам, включая время, когда игрок ушёл в другое приложение. Первое тикает
только пока игровой экран на переднем плане. Для оценки нагрузки нужно оно.

Оговорка: у сессий до сентября 2026 `activeTimeMs` восстановлен как
`endTime − startTime`, то есть завышен. Отличить можно по дате.

## `/v1/meta`

Одна строка. Читайте её перед первым запросом: дёшево и сразу видно,
есть ли данные и совпадают ли ожидания.

| Колонка | Что значит |
|---|---|
| `contract_version` | Версия этого контракта, сейчас 1 |
| `app_version_name` | Версия Play of Time, например `15.06` |
| `schema_version` | Версия схемы базы |
| `aim_ms` | Цель в миллисекундах. Сейчас всегда 3000 |
| `attempts_total` | Всего попыток |
| `sessions_total` | Всего сессий |
| `first_attempt_at` | Самая ранняя попытка, epoch ms. 0 если данных нет |

## Что нужно знать про изменения

Имена колонок в `/v1/...` не меняются. Если понадобится несовместимое
изменение, появится `/v2/...`, а `/v1/...` продолжит работать.

Колонки могут **добавляться**. Не полагайтесь на порядок колонок в курсоре
и на их количество — берите по имени.

## Чего пока нет

**Уведомлений об изменениях.** Опрашивайте сами. Если нужен
`ContentObserver` — скажите, включим.

**Отбора по датам и постраничной выдачи.** Отдаётся всё.

**Признака сброса данных.** У игрока есть кнопка полного стирания истории,
после неё идентификаторы начинаются заново. Сейчас вы этого не увидите и
решите, что данные изменились задним числом. Если для вас это важно —
добавим счётчик сбросов в `meta`.

Отдельно: адреса `/v1/export/...` в этом же провайдере — внутренние, закрыты
подписью, нужны для переноса истории между версиями самого Play of Time.
Вам они недоступны и не нужны.
